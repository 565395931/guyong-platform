# 拼多多工作台 UIA 可行性检测报告

- 检测时间：2026-10-13 11:1x – 11:3x（本地时间）
- 检测对象：拼多多工作台 3.7.2.14（`C:\Program Files (x86)\pinduoduo\3.7.2.14\`，
  内核 `pddbrowser104`，定制 Chromium 104）
- 方法：沿用飞鸽/千帆流程——Win32 枚举窗口 → 附加主窗口/全部
  `Chrome_RenderWidgetHostHWND` 渲染宿主 → dump UIA 元素树（只读）
- 复检入口：`python probe.py`（客户端升级后重跑；`--warmup N` 可加预热观察）

> ## 结论：**不可读**
>
> 拼多多工作台**不暴露 UI Automation 无障碍树**：主窗口下 4 个渲染宿主全部返回
> **0 个文本节点**，全窗口扫描（51 个候选目标）只拿到窗口框架类元素（标题栏/最小化/关闭），
> 拿不到任何页面内容。与飞鸽/千帆"附加渲染宿主即可读全量树"形成鲜明对比。

## 1. 结构发现（供参考）

| 窗口 | 类 | 说明 |
| --- | --- | --- |
| 主窗口（hwnd 1050350，1250x790，标题"拼多多工作台"） | `g_wszPDDWindowClass{E77EAED1-…}` | 自绘类名；下挂 **4 个** `Chrome_RenderWidgetHostHWND`（全为 vis=0，经隐藏的 `Chrome_WidgetWin_0` 容器） |
| 消息提示浮窗 | `MessageNoticeWnd` / `UrgentMessageNoticeWnd` / `ContactTipWnd` | 自绘弹窗（含一个 vis=1 的"消息提示"） |
| 多多进宝聊天 | `jinbaochatwnd` | 独立聊天窗（当前隐藏） |
| 各种辅助窗 | `PerryShadowWnd` / `CUrgentTip`（催一催）/ `OperationPopupWnd` 等 | 均为自绘 |

进程架构：`PddWorkbench.exe`（外壳）→ `pddwebworkbench.exe` ×多个（Chromium 多进程）。

## 2. 证据链（为什么判定不可读）

1. **渲染宿主无文本**：4 个 `Chrome_RenderWidgetHostHWND` 附加成功但文本节点恒为 0；
   主窗口自身只有 1 个文本（窗口标题），其下仅一个空 `PaneControl`。
2. **全量扫描**：46 个拼多多相关顶层窗口 + 全部渲染宿主逐一附加，有内容的只有
   窗口框架元素（如某隐藏 Chrome 窗口读到"最小化/最大化/关闭"，属系统边框，非业务内容）。
3. **长时预热无效**：Chromium 无障碍树是"检测到 UIA 客户端后异步构建"的（飞鸽实测约 15s），
   本次连续轮询 16s + 数十分钟间断附加观察，文本数始终为 0——不是预热问题，
   是**定制内核未启用/剥离了无障碍支持**。
4. **无调试通道**：相关进程未监听任何 TCP 端口；命令行（`--browser-ipc-channel=…`
   自定义私有 IPC、`--ir-plugin-*` 本地插件壳）中没有 `--remote-debugging-port` 等调试参数。
   （对比：千帆客户端开着 node inspector 端口——那个也不能用，但至少存在；PDD 连这个都没有。）

## 3. 可行路线（按推荐排序）

### 3.1 网页版 mms.pinduoduo.com + 浏览器自动化 ★推荐

**关键证据**：客户端命令行显示它加载的就是
`--ir-url-host=mms.pinduoduo.com --ir-url-path=/web/`——**工作台本身就是这个网页 + 定制外壳**。
也就是说同样一套界面在普通浏览器里就能打开，而浏览器里我们有完整的 DOM 能力
（读、写、不受窗口可见性限制）。本机可用浏览器自动化工具（browser-use）。
代价：需要商家账号**扫码登录一次**（会话可保存在持久化浏览器配置里）。

### 3.2 截图 + OCR（兜底）

- 本机 Python 未装第三方 OCR 包；**Windows 11 自带 OCR（WinRT）可用**，不依赖外网。
- 局限：只能读"当前可见"的区域（列表要边滚边截）、丢失元素结构、对悬浮态/非文本内容
  （头像、商品卡图）无能；仅建议用于少量关键字段的兜底校验，不适合做主线。

### 3.3 订单侧其实不必依赖客户端

仓库的 `pinduoduo-commerce` 适配器已声明订单/售后事件能力（`pinduoduoAdapter`，
官方开放平台通路）；本机日志显示 `pinduoduo.sync_tick_completed accounts:0`——
**没有配过账号**所以没数据。聊天则无官方 API（能力矩阵：官方商家 API 不提供买家聊天收发）。

## 4. 结论与下一步

- UIA 路线对拼多多工作台**已排除**（探针保留，客户端升级后可复检）。
- 推荐走 **3.1 网页版自动化**：聊天读写与订单抓取都可行，技术栈与现有一致（浏览器自动化
  而不是 UIA）。动工前需要：商家账号扫码登录一次 + 确认以网页版为准（双端同时登录是否
  互踢需实测）。
- 若坚持不碰网页版，再评估 3.2 的 OCR 方案（成本高、可靠性明显更低）。

## 5. 更新（2026-10-13 下午）：视觉读取路线打通 + 客户端升级到 3.7.3.12

- **客户端自动升级 3.7.2.14 → 3.7.3.12**（升级包今早已暂存，重启时应用；升级后需重新登录一次）。
  新版两套内核（`pddbrowser104` / `pddbrowser`）的无障碍字符串与旧版一致：
  有 `--force-renderer-accessibility`（1 处）、**无 `UiaClientsAreListening`**（自动唤醒路径被切除），
  UIA 仍不可读。
- **视觉读取路线（截图 + OCR）已打通并工具化**：
  - 截图：`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` 实测可用，**窗口被其他窗口遮挡也能截**，
    不需要置顶、不抢前台（对本客户端 DirectComposition 渲染同样有效）；
  - OCR：Windows 自带 `Windows.Media.Ocr`（zh-Hans-CN），输出每行文本 + 屏幕坐标；
  - **编码坑**：PowerShell 5.1 接收 WinRT 字符串会经 ANSI 代码页损坏（UTF-8 字节被按 GBK 解读），
    调用前 `chcp 65001` 即修复（实测）；
  - 工具：`pdd_client.py`（`capture` / `read`）+ `ocr.ps1`；实测读取工作台界面 **11 行文本**
    （会话列表"官方待办任务群 VIP / 拼多多米白白 / 官方群消息"、提示条、页签等，坐标齐全）。
  - OCR 质量：常用字词准确率约七八成，数字/常见词良好；生僻组合会错（旗舰→视店、响→啊），
    精确定位场景（订单号等）需局部放大裁剪后单独识别验证。
- 深度检测记录（全部只读/可逆）：`SPI_SETSCREENREADER` 系统屏幕阅读器标志实测**无法唤醒**
  该内核的无障碍树（设置后 40 秒无变化，已还原标志）；相关进程无监听端口、无调试参数。
- **未决**：`--force-renderer-accessibility` 的启动参数透传实验被版本升级打断
  （外壳 `PddWorkbench.exe` 是否把未知参数转发给浏览器进程未确认），登录后可重试。

## 6. 方案 B 结果（2026-10-13 傍晚）：启动参数路线不可行

在 3.7.3.12（已升级、无更新干扰）上做了干净的透传实验：

- `PddWorkbench.exe --force-renderer-accessibility` 启动后，浏览器主进程（`browser-ipc-channel`
  那个）**10 秒内正常出现，但命令行里没有该参数**——外壳不接受/不转发未知参数（实测存档
  `out/pdd_browser_cmdline_before.txt` / `after.txt` 对比）。
- 参数模板不在任何根目录 DLL 里（全目录扫描 `--ir-url-host` / `pddwebworkbench.exe` 引用，
  只在浏览器自身与 sentinel 出现）——外壳动态/混淆构造启动参数，**没有配置文件入口**。
- 直接启动 `pddwebworkbench.exe` 并自带参数：不可行——外壳负责的私有 IPC 通道
  （`--browser-ipc-channel`）与加密配置（`--extra-cmd` 十六进制块）都拿不到，页面与外壳窗口
  无法正确结合。
- 注册表级进程劫持（IFEO "Debugger"）理论上能强塞参数，但：客户机装有风控组件
  `sentinel.exe`（32MB），注册表劫持有触发风控的风险；且**每次重启客户端都要求重新登录**
  （两次实验都验证了），调试成本高。**结论：不建议走这条路**，除非将来有客户侧官方支持。

**附带实测结论**：本客户端每次强制重启后都需要重新手机扫码登录（登录态不随进程重启保留），
任何涉及重启的调试都需要用户配合扫码。视觉路线（第 5 节）不受影响。

### 关键踩坑：后台窗口的"旧帧"陷阱（已修复）

**客户端窗口不在前台时，Chromium 停止渲染，PrintWindow 截到的是停更的旧画面。**
实测经过：回车发送后立刻截图核对，画面仍显示输入框有字（旧帧），误判"回车未发送"，
又点了发送按钮 —— **同一条消息发了两遍**。点按钮顺带提窗后画面恢复实时，两条都显出来。
修复：`capture_and_ocr` 默认先校验前台（非前台自动提窗 + 0.8s 等待），`--no-raise` 可跳过。
教训：**任何"操作后立即核对"的截图都必须先确保窗口在前台**，否则读到的是过期状态。
