# 客户管理、日报与对话工作台联动设计

## 1. 背景

系统已经具备客户列表、客户画像、每日沟通统计、成交后复联任务和三层角色权限，但客户数据与对话工作台仍是两个相对独立的操作面：

- 客户画像只能按渠道和账号跳转，不能准确选中原会话。
- 日报主要用于查看，不能直接驱动客服当天的处理动作。
- 对话工作台缺少客户阶段、AI 画像、订单和复联任务的统一上下文。
- 客服在对话、客户列表、画像和日报之间切换时，筛选状态容易丢失。

本设计在不改变左侧导航、路由层级和现有工作台主布局的前提下，把客户、会话、消息、订单、沟通日、画像、跟进和日报连接为统一的“客户工作上下文”。

## 2. 已确认的产品决策

1. 采用“对话优先”工作流：客服主要在对话工作台完成日常处理，客户页和日报负责检索、复盘、批量操作和主管下钻。
2. 客户上下文使用按需打开的右侧抽屉，不长期占用聊天宽度。
3. 日报中的客户可直接进入准确会话，并自动打开客户抽屉。
4. 使用统一客户工作上下文，所有页面共用同一客户身份、阶段、画像、订单和任务状态。
5. AI 可自动更新画像、阶段、风险、优先级和建议复联时间；会话处于 AI 接待模式时，回复通过翻译与质量检查后可自动发送。人工接管时由客服选择原文或翻译发送。
6. 左侧导航、侧栏宽度、折叠逻辑、移动端行为和现有路由结构不变。

## 3. 目标与非目标

### 3.1 目标

- 从客户列表、日报或画像页准确定位到具体会话。
- 在对话中完成客户判断、成交标记、跟进安排和画像修正，不强制离开聊天上下文。
- 把日报从静态统计升级为可筛选、可下钻、可执行的每日工作台。
- 让 AI 画像可解释、可纠正、可追溯，并用新证据自动修正。
- 普通用户、主管和管理员在同一套界面中获得符合权限的数据与操作。
- 对重复消息、重复订单事件、AI 失败和无会话客户提供确定性处理。

### 3.2 非目标

- 不新增或重排左侧导航项目。
- 不重做消息收发、会话池或订单核心流程。
- 不允许 AI 绕过会话接待模式、翻译状态、质量检查或发送权限直接发消息。
- 不推断疾病、人格障碍、政治、宗教或其他不必要的敏感属性。
- 本阶段不引入独立消息总线；保留事件记录边界，为后续演进预留空间。

## 4. 核心使用流程

### 4.1 对话处理

1. 客服在会话列表选中会话。
2. 工作台根据 `conversationId` 解析客户身份并加载统一客户上下文。
3. 客服点击客户入口后，从右侧打开抽屉；聊天主区保持当前会话和滚动位置。
4. 抽屉默认显示智能概览，客服可切换沟通时间线、跟进任务和订单信息。
5. 客服可完成本次沟通、标记成交、安排跟进、修正画像或打开完整画像。
6. 新消息、订单或任务状态变化后，只刷新受影响的客户上下文，不重置当前会话。

### 4.2 日报处理

1. 普通用户打开自己的今日工作台；主管或管理员可选择负责人和团队范围。
2. 用户通过阶段、意向、成交、跟进状态、渠道或异常类型筛选客户。
3. 点击客户时，跳转到 `/platform-messages`，携带渠道、账号、具体会话 ID、客户 ID 和抽屉打开状态。
4. 对话页加载目标会话；若该会话不在当前池或当前分页，按 ID 单独读取并选中。
5. 浏览器返回日报时恢复日期、筛选、页码和滚动位置。

### 4.3 无会话客户

日报或画像中没有可用会话的客户显示“待关联”。主管和管理员可从有权限的候选会话中选择绑定；普通用户只能查看提示，不能跨负责人绑定。

## 5. 对话页客户抽屉

抽屉覆盖在工作台右侧，默认关闭。打开后不挤压左侧导航和会话列表；桌面端宽度在 420 至 520 像素之间，窄屏使用全宽抽屉。关闭后聊天区恢复原宽度。

### 5.1 智能概览

- 客户名称、渠道身份、负责人、人工标签。
- 首次、二次、三次及后续沟通阶段和累计沟通日。
- 购买意向、价格敏感度、决策节奏、沟通偏好、核心需求和主要顾虑。
- 最近沟通摘要、意向变化、风险提示、下一步目标和建议话术。
- 下次跟进时间、优先级、生成来源、置信度和判断依据。
- 成交状态、最近订单和售后风险。

### 5.2 沟通时间线

- 按 `APP_TIMEZONE` 自然日归并消息，同一客户同一天只算一次沟通。
- 每个沟通日显示阶段、消息数、摘要、关键需求、异议、关联会话和负责人。
- 阶段变化和 AI 画像变化以事件形式插入时间线，并展示触发证据。

### 5.3 跟进任务

- 显示待处理、到期、超期、已完成、已跳过和已取消任务。
- 支持完成、跳过、延期、指定时间、填写原因和人工锁定。
- 完成成交首次复联后按规则创建下一次复联；重复操作不得创建重复任务。

### 5.4 订单信息

- 显示订单状态、金额、商品、成交时间、退款和售后状态。
- 订单进入 `paid`、`delivered` 或 `closed` 后触发成交状态及首次复联。
- 订单取消或退款时只取消对应订单尚未完成的自动任务，不删除人工任务和历史审计。

### 5.5 固定操作区

抽屉底部提供“完成本次沟通”“标记成交”“安排跟进”“打开完整画像”。按钮按权限和当前状态显示；提交期间禁用重复操作，并给出明确成功或失败反馈。

现有“用户信息”和“快捷话术”能力保留，合并到同一按需辅助抽屉的页签体系中，不再形成第二个同时占宽的右侧面板。

## 6. 日报工作台

日报使用“可视化概览 + 可操作客户清单”，避免只提供静态表格。

### 6.1 指标与图形

- 今日沟通客户数。
- 首次、二次、三次及后续沟通分布。
- 成交数、待跟进数、超期数、跟进完成率。
- 意向升高、意向降低和长时间未回复数。
- 沟通阶段漏斗、意向分布、成交趋势和负责人工作量。

### 6.2 客户行动清单

每行显示客户、负责人、渠道、沟通阶段、今日摘要、意向、风险、成交状态、下次动作和到期时间。支持：

- 按负责人、渠道、阶段、意向、成交和跟进状态筛选。
- 按超期、意向升高、长时间未回复和成交待复联快速筛选。
- 点击客户进入准确会话并打开客户抽屉。
- 主管批量分配负责人和添加人工标签。
- 导出图片和打印，导出内容包含当前筛选说明和生成时间。

### 6.3 快照规则

当天数据可实时聚合；跨日后保存日报快照。历史日报读取快照，后续画像变化不会改写过去结果。手动重新生成会创建新版本并保留生成者、时间和上一版本审计信息。

快照冻结统计事实，不冻结访问权限。读取、下钻、打印和导出历史快照时必须按当前权限重新过滤；客户转交后，原负责人不能因为快照中曾包含该客户而继续查看详情。主管和管理员的历史审计范围继续遵循当前团队和系统权限。

## 7. 统一客户工作上下文

### 7.1 聚合边界

统一上下文由客户运营服务聚合，页面不再分别拼接多个互相独立的判断结果。上下文包含：

```json
{
  "customer": {},
  "activeConversation": {},
  "identities": [],
  "communicationStage": {},
  "aiProfile": {},
  "profileChanges": [],
  "communicationDays": [],
  "followups": [],
  "orders": [],
  "permissions": {},
  "generatedAt": "ISO-8601"
}
```

`permissions` 由后端按当前用户生成，前端只用它控制展示；后端仍对每个读取和修改操作重新鉴权。

对话抽屉使用按会话加载的轻量上下文，只返回首屏概览、待办和最近订单；时间线、全部订单和审计历史按页签懒加载。客户画像页可以使用按客户加载的完整上下文，避免客服连续切换会话时反复执行重型聚合。

### 7.2 会话深链

对话页查询参数使用：

- `channel`：渠道过滤。
- `account`：账号过滤。
- `conversation`：必须选中的具体会话 ID。
- `customer`：预期客户 ID，用于防止错误关联。
- `panel=customer`：加载后自动打开客户抽屉。
- `return`：站内返回状态键，不直接接受任意外部 URL。

目标会话不在当前列表时，工作台通过单会话接口加载。若用户无权访问，统一返回 404 并保留当前工作台，不泄露资源是否存在。

`conversation` 是唯一定位键，`channel`、`account` 和会话池只用于加载后的界面提示，不能用于猜测目标会话。消息页同步查询参数时必须保留 `conversation`、`customer`、`panel` 和 `return`，直到用户主动选择其他会话或关闭返回上下文。

### 7.3 API 增量

在现有接口基础上增加或扩展：

- `GET /api/v1/conversations/:id/customer-context`：按会话解析并返回轻量客户上下文。
- `GET /api/v1/customers/:id/workspace-context`：画像页或客户页按客户加载同结构上下文，可带 `conversation_id`。
- `PATCH /api/v1/customers/:id/owner`：主管或管理员分配负责人。
- `POST /api/v1/customers/:id/tags`、`DELETE /api/v1/customers/:id/tags/:tagId`：维护人工标签。
- `POST /api/v1/customers/:id/followups`：创建人工跟进任务。
- `PATCH /api/v1/customers/:id/ai-profile`：提交带版本号的人工修正和原因，不直接覆盖 AI 原始审计结果。
- `DELETE /api/v1/customers/:id/ai-profile/corrections/:correctionId`：撤销人工修正并创建反向审计事件。
- `GET /api/v1/customers/:id/audit-logs`：按权限分页读取画像变化和人工操作历史。
- `POST /api/v1/customers/:id/conversations/link`：主管或管理员关联会话。
- 扩展 `GET /api/v1/customers/daily-report`：返回图形指标、异常计数、负责人分布、主会话，以及 `mode=live|snapshot`、`revision`、`generatedAt`、`asOf` 和生成状态。

现有成交与跟进接口继续使用，不创建语义重复的新接口。

所有写接口携带 `expectedVersion`；当画像、负责人或跟进任务已被其他页面更新时返回 `409` 和最新版本，前端提示用户刷新后重试，防止抽屉、画像和日报相互覆盖。

### 7.4 数据增量

沿用现有 `customers`、`customer_identities`、`customer_communication_days`、`customer_followups`、`customer_daily_reports` 和 `customer_ai_audit_logs`。新增数据必须采用幂等迁移：

- `customer_tags`：客户、标签、来源、锁定状态、创建者和时间。
- `customer_profile_corrections`：修正字段、原值、修正值、原因、操作者和时间。
- `customer_communication_events`：以消息 ID 或稳定外部事件 ID 为幂等键，避免历史导入和重试重复增加 `message_count`。
- `customer_operation_events`：保存待处理事件、处理状态、重试次数和租约，用作数据库型 outbox，确保消息或订单落库后可重放客户运营更新。
- 日报表增加快照版本和上一版本引用，或在现有 `details` JSON 中提供兼容版本字段。
- 会话和日报响应补充 `customer_id`、`primary_conversation_id`，不复制客户主数据。
- 订单稳定 `customer_id` 是本联动功能的上线前置条件；手机号仅作为首次匹配线索。历史订单无法唯一回填时标记“待关联”，禁止按手机号自动合并或向客户上下文返回明细。

任务、画像证据、沟通摘要、订单和画像变化保留 `source_conversation_id` 与 `owner_id`。普通用户响应按来源会话再次裁剪，不能看到由其他负责人不可见会话生成的证据片段或衍生结论。

`customer_identities` 对空账号使用规范化账号键或生成列建立真实唯一约束，避免 MySQL 中 `NULL` 参与唯一键时允许重复身份。

## 8. AI 画像与心理学使用边界

AI 输入只使用业务范围内的账号资料、聊天内容、回复节奏、沟通日、订单和跟进结果。输出包括：

- 购买意向、决策节奏、价格敏感度、沟通偏好、核心需求和主要顾虑。
- 每个信号的证据摘要、置信度、更新时间和模型来源。
- 画像相对上一版本的变化以及变化原因。
- 下一次沟通目标、建议时间、优先级和建议话术。

规则：

1. 不产生临床诊断或不必要的敏感属性推断。
2. 没有证据的信号不得展示为确定事实。
3. 人工锁定的负责人、标签和任务时间不能被 AI 覆盖。
4. 人工修正进入后续 AI 上下文，但原始判断和修正都保留在审计日志中。
5. AI 超时、格式错误或不可用时保留旧画像，任务时间回退到确定性规则；消息和订单事务不回滚。
6. AI 生成统一的结构化回复。会话处于 AI 接待模式且翻译、实体一致性和质量检查全部通过时可自动发送；人工接待模式只提供建议话术，由客服触发发送。
7. 客户消息一律视为不可信数据，使用明确数据边界传给模型，消息内容不能改变系统指令、输出契约或权限。
8. 画像模型不具备工具调用、网络访问或消息发送权限；输出必须通过严格 JSON Schema、枚举、长度和日期范围校验。
9. AI 审计只保存最小必要的证据摘要，不保存完整聊天原文、访问令牌或其他凭据。

画像字段使用版本化结构：`value`、`evidence`、`confidence`、`source`、`model`、`asOf`、`lockedByHuman` 和 `version`。AI worker 领取数据库租约，并在回写时比较画像版本；如果人工在生成期间已经修改画像，AI 结果只写审计而不覆盖新版本。

## 9. 自动化与一致性

- 消息或订单与客户运营事件在同一事务中落库；后台 worker 消费可重放事件。AI 自动出站消息不创建新的沟通日。
- 唯一键 `(customer_id, communication_date)` 保证同日只生成一个沟通日。
- 每条消息再通过稳定事件 ID 幂等，避免重复增加当日 `message_count`。
- 订单和任务事件使用业务幂等键，重试不会重复创建成交或复联任务。
- 默认成交首次复联为 10 天，完成后下一次为 15 天；AI 可调整未锁定任务。
- 到期、超期、意向显著变化和长时间未回复进入待办及日报异常筛选。
- 客户上下文写操作完成后，前端失效对应客户缓存并局部刷新；不重载整个工作台。
- 客户身份解析、客户创建、身份绑定、沟通日更新和阶段重排在事务中执行；并发首条消息不会产生重复客户或孤立身份。
- 多实例 worker 使用数据库 claim/lease，不依赖单进程内存锁防重。
- 标记成交、完成或跳过任务、创建下一任务、关联会话和日报重生成在事务中完成状态条件更新、审计和 outbox 写入。
- 上述复合命令同时校验 `expectedVersion`、合法状态迁移和作用域化 `Idempotency-Key`；相同幂等键重试返回第一次结果。

## 10. 权限与安全

- 普通用户只能读取和操作 `owner_id`、`claimed_by` 或 `agent_id` 属于自己的客户、会话、订单摘要和任务。
- 主管和管理员可查看全量；负责人分配和会话关联只允许主管和管理员执行。
- 管理员保留系统级配置能力，本设计不改变账号权限模型。
- 无权资源统一返回 404；参数使用结构化校验，数据库查询全部参数化。
- `return` 参数只能引用受控的站内状态键，禁止开放重定向。
- 导出内容遵循当前查询权限，不在浏览器端缓存全量团队数据。
- 分配、关联、画像修正、成交、任务调整和日报重生成全部写入审计日志。
- 普通用户对客户的可见性按当前身份和任务边界裁剪；命中客户的一条负责会话，不代表可以读取其他负责人会话产生的私有任务或明细。
- 跟进写操作除校验客户可见性外，还必须校验 `assigned_to` 或绑定会话；主管和管理员除外。
- 统一修复所有客户更新接口的对象级权限，通用客户 `PUT/PATCH` 不得绕过 `customerVisibility`。
- 统一普通用户角色契约：认证中的普通用户与会话坐席使用同一规范角色，避免能看客户却不能打开会话；迁移期兼容旧 `user` 和 `agent`，但授权策略只维护一份。
- 会话通用更新接口不得允许普通用户修改 `agent_id`；负责人重分配只能走主管或管理员专用接口。
- 除测试显式注入外，任何环境缺少 JWT 密钥都必须启动失败，不允许固定回退密钥。认证中间件统一固定允许的 JWT 算法、`issuer` 和 `audience`，并校验用户仍处于启用状态。
- 日报日期、负责人、分页、枚举、修正原因和导出范围使用统一 schema 校验；重生成、AI 重算和导出接口限流。
- 发送给 AI 的账号标识和聊天内容按最小必要原则脱敏，并配置保留周期；AI 输出只按文本转义渲染，禁止直接使用 `v-html`。
- 旧会话写入口必须在本功能上线前统一收口：`PATCH /conversations/:id` 不接受普通用户修改负责人；`assign`、`transfer` 和携带 `seat_id` 的 `claim` 只允许主管或管理员，并校验目标用户状态、角色、账号绑定和团队范围。
- 批量头像回填、全量历史同步等全局副作用接口只允许管理员或获授权主管按账号范围启动；任务状态只允许创建者、授权主管或管理员读取，并设置用户级限流、并发上限和审计。
- 关联会话时验证客户与会话都在操作者范围内；一个有效身份只能绑定一个客户。已有绑定不能静默改挂，冲突返回 `409`；改挂必须填写原因并审计前后值。
- 批量分配和批量标签限制单次数量，先校验全部对象权限，再在事务中全成功或全失败。
- 日报图片和打印使用字段白名单，对手机号、备注和 AI 证据脱敏。导出生成与下载都重新鉴权，制品使用不可猜测 ID、短时有效期、私有缓存，并审计操作者、筛选、记录数和下载时间；不得先把全团队数据下发浏览器再截图。

## 11. 状态恢复与错误处理

- 客户列表和日报把日期、筛选、页码、滚动位置写入路由查询或会话级状态缓存。
- 深链会话加载失败时显示可重试提示，不清空当前已选会话。
- 客户上下文部分字段失败时显示分区错误；已成功的数据仍可使用。
- AI 正在生成时显示上一次结果和“更新中”，不显示空白骨架替换现有数据。
- 提交动作使用幂等保护和加载状态；失败后保留用户输入。
- 无绑定客户时显示“待关联”，不得猜测并打开相似会话。

## 12. 测试策略

### 12.1 单元测试

- 深链参数归一化、受控返回状态和目标会话选择。
- 客户上下文响应归一化、权限按钮、画像变化和日报指标计算。
- 同日沟通幂等、阶段计算、任务日期、人工锁定和 AI 回退。

### 12.2 集成测试

- 按会话和按客户获取统一上下文，验证普通用户与主管权限。
- 日报筛选、快照版本、会话深链和无会话客户。
- 负责人分配、标签、画像修正、会话关联、成交与任务操作的审计和幂等性。
- 重复消息、重复订单事件和 AI 失败不产生重复记录。
- 并发首条消息、多 worker 领取、人工修改与 AI 回写竞争返回确定结果。
- 普通用户、旧 `user`、坐席 `agent`、主管和管理员的对象级权限矩阵。
- 固定 JWT 回退被拒绝，算法、签发方、受众和禁用用户校验生效。
- 旧 `assign`、`transfer`、带目标坐席的 `claim`、全量同步和批量任务接口不能被普通用户调用。
- 同号、复用号码和无法唯一回填的历史订单不会错误进入客户上下文。
- 历史日报按当前权限过滤，转交后的原负责人不能下钻或导出客户详情。
- AI 提示注入样本不能改变画像 schema、触发工具或输出未授权内容。

### 12.3 端到端测试

- 日报筛选客户，进入准确会话并自动打开抽屉。
- 在抽屉完成跟进或标记成交，日报对应数据局部更新。
- 普通用户不能通过修改 URL 访问其他负责人的会话或客户。
- 浏览器返回后恢复日报或客户列表状态。
- 桌面和移动视口中抽屉不遮挡关键操作，文本不溢出。
- 现有左侧导航、折叠和渠道页面回归测试保持通过。

## 13. 验收标准

1. 从日报、客户列表和画像页进入对话时准确选中目标会话，并按需要自动打开客户抽屉。
2. 客服能在不离开对话的情况下查看客户阶段、画像、时间线、任务和订单，并完成常用操作。
3. 同一客户同一天多轮消息只算一次沟通，跨日阶段和日报统计一致。
4. 日报包含可视化指标、异常筛选、客户行动清单、负责人下钻、图片导出和历史快照。
5. AI 判断显示证据、置信度和变化原因；人工修正与锁定不会被后续 AI 覆盖。
6. 普通用户无法读取或修改其他负责人的客户和会话；主管和管理员可按权限查看全量并分配。
7. 重复事件、AI 失败和网络重试不会重复创建沟通日、成交状态或复联任务。
8. 左侧导航、现有路由结构、会话收发、订单能力和移动端侧栏行为不发生回归。
9. 客户更新、会话更新和跟进写操作不存在通过猜测 ID 越权修改其他负责人数据的路径。
10. 历史日报读取冻结快照；重新生成产生可审计版本，到期但当天未沟通的客户仍进入行动清单。
11. 固定 JWT 回退、旧会话分配越权和客户更新 IDOR 在客户抽屉写操作开放前修复并通过鉴权测试。
12. 客户工作上下文中的订单、画像证据、任务和摘要都按稳定客户 ID、来源会话及当前权限返回，不因手机号或单条可见会话泄露其他负责人的数据。

## 14. 多语言翻译插件

### 14.1 产品目标

系统需要服务国外客户。翻译能力作为独立插件层接入消息链路，完成语言识别、双语展示、AI 自动回复翻译、人工回复语言选择、当地礼貌适配和客户语言画像更新。渠道适配器只负责消息收发，不实现各自独立的翻译逻辑。

插件不绑定单一厂商。首期可以使用现有 AI 服务作为翻译提供方，但业务层通过统一接口调用；后续可按语言、成本、延迟和故障状态切换专用翻译服务或备用模型。

### 14.2 当前语言与长期语言

- `currentReplyLanguage` 由客户最新一条有效入站消息决定。即使客户只发一句，也立即用该句语言回复。
- `preferredLanguage` 表示长期首选语言，根据历史使用占比和人工确认维护。
- 最新一句语言变化只影响当前回复语言，不直接覆盖长期首选语言。
- 客服可人工锁定长期首选语言；AI 和统计不能覆盖锁定值。
- 混合语言或识别置信度不足时，使用最近一次已确认语言，并提示客服确认。
- 国家或地区优先来自渠道资料、账号地区或客户主动提供的信息，不能仅凭语言确定。

### 14.3 入站消息

处理顺序：

`原始消息落库 → 创建翻译事件 → 语言识别 → 中文翻译 → 质量检查 → 保存双语结果 → 更新语言上下文与客户画像`

- 原始消息先落库，翻译失败不能阻止消息接收。
- 消息气泡显示客户原文和中文翻译，原文始终不可覆盖。
- 每条消息显示识别语言、翻译状态、置信度和必要的低置信度提示。
- 客服可以提交译文修正；修正生成新版本并保留机器译文、原译文和操作者审计。
- 语音、图片和附件的文字识别不属于本阶段必需范围，但插件接口保留 `contentType` 和提取文本字段。

### 14.4 AI 自动回复

AI 自动回复固定使用“跟随客户”模式：

1. 使用客户原文、中文翻译、客户上下文和可见历史生成结构化回复意图及中文标准稿。
2. 翻译插件按 `currentReplyLanguage`、客户术语和礼貌策略生成目标语言译文。
3. 执行金额、日期、地址、产品型号、否定词和承诺类表达的一致性检查。
4. 质量检查通过后才交给渠道发送。
5. 系统内保存并显示中文标准稿与实际发送文本。

翻译或质量检查超时、失败时，AI 回复进入“待处理”状态，不能把中文标准稿直接发送给国外客户。客服可重试、编辑目标语言译文或明确选择原文发送。

### 14.5 人工回复

人工输入区提供三个模式：

- `follow_customer`：默认模式，输入中文后翻译为客户当前语言发送。
- `original`：按客服输入原文发送，不做目标语言翻译。
- `specified_language`：仅本条或当前会话指定其他目标语言。

客服直接输入目标语言时不重复翻译，但仍生成中文对照。发送前显示最终译文并允许编辑；系统保存客服原稿、机器译文和最终发送版本。会话级选择不影响其他客户，客服可以将某次选择限定为“仅本条消息”。

客户切换语言后，下一条回复立即跟随新语言；输入框显示非阻断提示。涉及金额、日期、地址、产品规格、退款、交付承诺等高风险内容时，即使翻译置信度较高，也必须展示一致性检查结果。

### 14.6 文化礼貌适配

礼貌适配根据已确认的语言、国家或地区、渠道、客户历史偏好和业务场景调整：

- 称呼、问候、感谢、道歉和结束语。
- 正式程度、直接或委婉程度、回复长度和催促方式。
- 售前、成交、交付、退款和售后场景的表达边界。
- 客户已经接受的产品名、规格、品牌和固定译法。

文化建议必须显示依据和置信度，只用于改善表达，不生成民族性格标签，也不把国家常见习惯写成客户个人事实。无法确认地区时只采用语言通用礼貌规则。

### 14.7 翻译插件接口

插件层提供稳定业务接口：

```json
{
  "operation": "detect | translate | localize | quality_check",
  "sourceText": "string",
  "sourceLanguage": "BCP-47 or auto",
  "targetLanguage": "BCP-47",
  "contentType": "customer_message | ai_reply | human_reply",
  "localeContext": {
    "region": "BCP-47 region or null",
    "formality": "formal | neutral | casual",
    "scenario": "sales | followup | order | support",
    "glossaryVersion": 1
  },
  "idempotencyKey": "string"
}
```

统一响应包含 `detectedLanguage`、`translatedText`、`confidence`、`provider`、`model`、`qualityFlags`、`glossaryHits`、`version` 和 `processedAt`。所有提供方适配器必须遵守相同超时、重试、错误分类和观测指标。

处理管线固定为：

`语言识别 → 术语保护 → 语义翻译 → 礼貌本地化 → 实体一致性检查 → 严格结构校验`

系统、企业、产品和客户四层术语表按范围合并，客户人工确认的译法优先级最高。术语变更生成版本，历史消息继续引用当时版本，不在后台静默改写。

### 14.8 数据模型

新增或扩展：

1. `message_translations`
   - `message_id`、`source_language`、`target_language`、`original_text`、`zh_text`、`machine_text`、`final_text`、`status`、`confidence`、`provider`、`model`、`quality_flags`、`glossary_version`、`version`、`created_at`、`updated_at`。
   - 以消息、目标语言和版本建立唯一约束；原始消息不可覆盖。
2. `customer_language_profiles`
   - `customer_id`、`current_reply_language`、`preferred_language`、`preferred_locked_by`、`region`、`region_source`、`formality`、`communication_style`、`etiquette_advice`、`language_stats`、`version`、`updated_at`。
3. `translation_glossary_entries`
   - `scope_type`、`scope_id`、`source_language`、`target_language`、`source_term`、`target_term`、`case_sensitive`、`status`、`version`、`created_by`。
4. `translation_jobs`
   - `event_id`、`message_id`、`operation`、`status`、`attempts`、`provider`、`lease_until`、`last_error_code`、`idempotency_key` 和时间字段。

翻译任务使用数据库 claim/lease 和稳定消息事件 ID，可重试但不能产生互相冲突的最终译文。服务商凭据不写入上述业务表，只使用环境变量或现有加密凭据存储。

### 14.9 API 增量

- `GET /api/v1/conversations/:id/language-context`：读取当前语言、长期语言、地区、礼貌策略和允许的回复模式。
- `PATCH /api/v1/conversations/:id/language-mode`：设置当前会话或仅下一条消息的人工回复模式，带 `expectedVersion`。
- `POST /api/v1/conversations/:id/translation-preview`：按当前草稿、回复模式和目标语言生成可编辑预览，不发送消息。
- `POST /api/v1/messages/:id/translations/retry`：重试失败或低置信度翻译。
- `PATCH /api/v1/messages/:id/translations/:version`：提交最终译文修正和原因。
- `PATCH /api/v1/customers/:id/language-profile`：修正或锁定长期语言、地区、称呼和正式程度。
- `GET /api/v1/translation-glossary`、`POST /api/v1/translation-glossary`、`PATCH /api/v1/translation-glossary/:id`：主管维护企业和产品术语。
- 管理员在现有 AI/服务配置边界中配置翻译提供方、备用顺序、超时和保留期限，不在前端暴露密钥。

现有消息发送接口增加 `languageMode`、`targetLanguage`、`translationVersion` 和作用域化 `Idempotency-Key`。后端重新校验会话权限、翻译版本和最终文本，不能信任前端传来的权限或服务商结果。

### 14.10 客户画像、客户列表与日报

客户抽屉和完整画像增加“语言与沟通偏好”：

- 当前回复语言、长期首选语言、已使用语言占比和最近使用时间。
- 国家或地区及其来源、正式程度、称呼习惯和文化礼貌建议。
- 专业术语偏好、人工锁定状态、置信度和最近修正记录。

客户列表支持首选语言、国家或地区、置信度和翻译异常筛选。日报增加语言分布、各语言客户数、待翻译消息、翻译失败、低置信度和人工接管次数；点击指标可筛选客户并进入准确对话。日报客户摘要统一使用中文，原始消息和发送消息仍保留双语版本。

主管可以维护企业术语和语言策略；管理员可以配置翻译提供方和故障回退；普通用户只能修改自己负责会话的回复模式和可见客户的译文修正。

### 14.11 安全、隐私与故障处理

- 客户消息视为不可信数据，模型指令与消息数据严格分隔；消息不能改变翻译策略、工具权限或输出 schema。
- 翻译模型没有工具调用、网络访问、消息发送或权限修改能力。
- 输出通过严格 JSON Schema、语言枚举、长度限制和实体一致性校验，前端只按文本转义显示。
- 发送给外部服务的身份和聊天内容按最小必要原则脱敏，并配置数据保留期限。
- 翻译、修正、模式切换、术语变更和最终发送版本全部审计；普通用户只能读取自己负责客户的双语内容。
- 首选提供方失败时按策略切换备用提供方。全部失败时保留原文和草稿，不发送未经检查的文本。
- 同一消息的重试复用幂等键；提供方返回不同结果时创建候选版本，只有经过选定或质量检查的版本可成为 `final_text`。
- 自动发送只使用服务端已确认的最终版本，不能通过修改前端请求绕过翻译状态和质量门槛。

### 14.12 翻译测试与验收

单元测试覆盖语言识别归一化、最新消息语言选择、长期语言锁定、术语优先级、双语消息归一化、金额日期实体对齐和提供方故障分类。

集成测试覆盖入站翻译、AI 自动回复、人工三种发送模式、译文修正、服务商切换、幂等重试、版本冲突和四角色权限矩阵。

端到端测试至少覆盖：

1. 客户只发送一句西班牙语，AI 和人工默认回复立即使用西班牙语。
2. 系统同时显示客户原文与中文，以及中文回复原稿与实际发送译文。
3. 客户中途切换语言后，下一条回复跟随新语言，但长期首选语言不被立即覆盖。
4. 客服可对单条消息选择原文发送或指定其他语言，选择不会污染其他会话。
5. 金额、日期、地址、产品型号和否定表达在翻译前后保持一致。
6. 翻译服务超时或失败时 AI 不会直接发送中文，草稿可重试和人工接管。
7. 普通用户无法读取或修改其他负责人客户的双语消息、语言画像和术语。
8. 语言与礼貌建议出现在客户画像、抽屉和日报筛选中，且显示来源和置信度。
9. 提示注入样本不能改变翻译规则、输出格式或触发发送。
10. 左侧导航、会话收发、客户工作上下文和现有移动端行为保持不变。
